# Компромиссы и известные ограничения

Живой документ: когда принимаем осознанный компромисс или фиксируем известное
ограничение — добавляем запись сюда. Если записей станет слишком много —
разобьём на категории или отдельные файлы.

## Формат записи

- **Компромисс/ограничение** — что именно приняли.
- **Почему так** — обоснование.
- **Триггер пересмотра** — при каком условии возвращаемся к решению.
- **Варианты решения** — что делать, если триггер сработал.

## Записи

### 1. Палитра чанка — максимум 256 типов на чанк

- **Компромисс/ограничение:** `Chunk.data: [u8; 4096]` хранит индекс палитры
  (`u8`), поэтому в одном чанке не может быть больше 256 различных типов блоков.
  При 257-м типе `Chunk::set` паникует.
- **Почему так:** экономия памяти в 2× против прямого `u16` (4 КБ против 8 КБ на
  чанк) и компактный формат под будущие save/load; встроенных блоков ~10.
- **Триггер пересмотра:** моды/геймплей реально допускают >256 типов в пределах
  одного чанка 16×16×16 (крайне маловероятно).
- **Варианты решения:** индекс палитры `u16` (8 КБ/чанк), либо «глобальная
  палитра»-фолбэк для редких чанков (как в Minecraft).

### 2. `BlockId` — `u16`

- **Компромисс/ограничение:** числовой идентификатор блока — `u16`, т.е. не более
  65536 типов блоков в реестре.
- **Почему так:** компактно, на порядок больше реальных потребностей.
- **Триггер пересмотра:** превышение 65536 типов (теоретически, при огромном
  наборе модов).
- **Варианты решения:** расширить до `u32`.

### 3. `BlockId` непрозрачный и не сохраняется

- **Компромисс/ограничение:** числовой `BlockId` действителен только в рамках
  одной сессии; в save/load и по сети передаётся строковый `ResourceId`.
- **Почему так:** числовой id назначается при регистрации и нестабилен между
  сессиями; строка — стабильная идентичность.
- **Триггер пересмотра:** не ожидается — это принципиальное решение.
- **Варианты решения:** — (соблюдать всегда; никаких `BlockId` в персистентных
  данных).

### 4. Числовой id — по порядку регистрации

- **Компромисс/ограничение:** числовые id блоков назначаются последовательно при
  регистрации (`air` = 0, `unknown` = 1, встроенные дальше, моды — следом).
- **Почему так:** dense-массив без дыр, O(1) доступ по индексу.
- **Триггер пересмотра:** если появится требование к стабильности числовых id.
- **Варианты решения:** не делать числовой id стабильным — стабильность только у
  `ResourceId`.

### 5. Палитра без компактизации

- **Компромисс/ограничение:** после перезаписи блока другим типом старая запись
  остаётся в палитре (мёртвая), память не возвращается.
- **Почему так:** компактизация — лишняя сложность и накладные расходы; в MVP
  не нужна.
- **Триггер пересмотра:** рост мёртвых записей в палитре при активной перестройке
  чанков (редактирование мира) начнёт ощутимо тратить память.
- **Варианты решения:** периодическая компактизация палитры (пересборка `data`).

### 6. `debug_assert!` вместо `assert!`

- **Компромисс/ограничение:** второстепенные проверки выполняются только в debug;
  в release некорректные входы проходят молча (например,
  `ResourceId::new("", "")` в release создаст некорректный id).
- **Почему так:** производительность release-сборки (правило в `AGENTS.md`).
- **Триггер пересмотра:** если окажется, что какая-то проверка критична для
  корректности и её отсутствие в release ведёт к реальным багам.
- **Варианты решения:** перевести конкретную проверку в `assert!`/`Result`.

### 7. `hashbrown` без DoS-устойчивости

- **Компромисс/ограничение:** `World::chunks` и прочие map используют быстрый
  хешер (`foldhash` из `hashbrown`), уязвимый к hash-flooding.
- **Почему так:** ключи (`ChunkPos` и др.) внутренние, не атакер-контролируемые;
  выигрыш в скорости на горячем пути.
- **Триггер пересмотра:** если в map попадут ключи из недоверенного ввода
  (сеть/файлы).
- **Варианты решения:** для таких мест использовать DoS-устойчивый хешер
  (`std::HashMap` с SipHash) отдельно.

### 8. Нет блок-стейтов

- **Компромисс/ограничение:** у блоков нет «состояний» (ориентация,
  «затопленность» и т.п.); каждый вариант — отдельный `BlockId`.
- **Почему так:** в MVP блоки простые; стейты — усложнение реестра и хранения.
- **Триггер пересмотра:** появление блоков с ориентацией/состояниями (печи,
  ступени, трубы).
- **Варианты решения:** ввести блок-стейты поверх `BlockId` (id + state), как в
  Minecraft; может повлиять на `Chunk`/палитру.

### 9. `World` не владеет `BlockRegistry`

- **Компромисс/ограничение:** `World` хранит только данные (`seed` + чанки);
  `BlockRegistry` передаётся отдельно (генерации, мешингу).
- **Почему так:** разделение «данные vs определения блоков»; реестр — почти
  статическая структура.
- **Триггер пересмотра:** если окажется неудобно таскать реестр отдельно.
- **Варианты решения:** `World` может владеть `Arc<BlockRegistry>` для
  самодостаточности.

### 10. Высота мира пока не ограничена

- **Компромисс/ограничение:** `coord`/`World` ничего не знают про y-границы; любой
  `BlockPos.y` валиден. Террайн-ген работает от `y = 0`.
- **Почему так:** границы мира — забота генерации и коллизии, а не хранилища.
- **Триггер пересмотра:** добавление генерации террейна и коллизии.
- **Варианты решения:** ввести константу высоты и проверки на границах мира
  (блок вне мира = «не изменяем»/`None`). В будущем — минимальная высота мира
  **-128** (глубокие пещеры, как в новых версиях Minecraft), максимум ~256:
  `coord`/`World` уже корректно работают с отрицательным `y`, изменится генерация
  (3D-шум пещер) и вертикальный диапазон загрузки чанков клиентом.

### 11. f32 vs f64 и детерминизм — не решено

- **Компромисс/ограничение:** для float-математики (коллизия, raycast) ещё не
  выбран тип `f32`/`f64` и политика детерминизма.
- **Почему так:** вопрос встанет при реализации коллизии/raycast.
- **Триггер пересмотра:** шаги 12 (raycast) и 16 (collision).
- **Варианты решения:** `f64` + фиксированные правила для воспроизводимости, либо
  целочисленный DDA для raycast и т.д.
